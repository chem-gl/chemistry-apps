# Informe: estándares para apps libres

**Fecha:** 2026-09-23  
**Stack:** Django 6, DRF 3.18, Celery 5.6, Redis 7, SimpleJWT, Nginx, Angular 21.

## Pregunta
¿Qué patrones actuales son seguros y operables para: (1) limitar concurrencia por IP, (2) limitar payloads/archivos, (3) publicar catálogos públicos de referencia y (4) almacenar resultados localmente en Angular?

## Método
Revisión de documentación primaria vigente (Django 6.0/6.1, DRF, Celery 5.6, Redis, Nginx, MDN y OWASP), contrastada con el modelo de ejecución del stack. Consulta realizada el 2026-09-23. Se priorizó semántica oficial sobre snippets de terceros.

## Hallazgos

### 1. Límite de concurrencia por IP (no tasa)

1. **Implementar un lease, no un contador de requests.** Para cada IP normalizada use un token aleatorio por trabajo, duración máxima y límite `L`. Un script Lua debe, en una operación atómica, eliminar leases vencidos, comprobar `ZCARD < L`, insertar `token -> deadline` y fijar TTL; devolver `token` o “full”. Use Redis `TIME` dentro del script o un reloj coherente. La atomicidad de scripts evita el TOCTOU entre “contar” y “crear”. Fuente: [Redis programmability](https://redis.io/docs/latest/develop/programmability/), [Lua API](https://redis.io/docs/latest/develop/programmability/lua-api/).
2. **Preferir sorted set por IP (`lease:{version}:{ip_hash}`).** Score = vencimiento; `ZREMRANGEBYSCORE` limpia huérfanos; `ZADD` registra el lease; `ZREM` libera solo el token. Borre la key cuando quede vacía y establezca TTL para dejar una red de seguridad. `SET key value NX EX` es excelente para un único lock, no suficiente por sí solo para un semáforo de `L > 1`. Fuente: [Redis SET (NX/EX)](https://redis.io/docs/latest/commands/set/).
3. **Liberar en Celery, no en la request.** Adjunte `lease_token` e IP hash a los argumentos/headers del task; libere en `Task.after_return()` (idempotente) o en `task_postrun`, que es el punto común posterior a la ejecución. Mantenga handlers explícitos para `task_failure`/revocación según la política. No libere en `task_success` únicamente: excepciones y rutas de retry dejarían fugas. Fuente: [Celery task signals](https://docs.celeryq.dev/en/stable/userguide/signals.html), [Celery tasks / after_return](https://docs.celeryq.dev/en/stable/userguide/tasks.html).
4. **Tratar el TTL como garantía, no como limpieza opcional.** Worker muerto, `SIGKILL`, pérdida de red o crash pueden impedir cualquier callback. El TTL debe ser mayor que el SLA esperado y menor que el máximo aceptable de bloqueo; para trabajos largos, heartbeat/renovación Lua con verificación de token. En retry, conservar el mismo lease si es la misma ejecución lógica, o liberar/re-adquirir explícitamente; nunca crear uno nuevo sin idempotencia.
5. **No usar `INCR`+`EXPIRE` como semáforo ingenuo.** Es vulnerable a carreras entre comandos y a contadores que no representan leases individuales; `EXPIRE` puede no ejecutarse si el proceso falla. Token bucket y fixed-window solucionan tasa, no concurrencia. Un zset sin limpieza, sin TTL o con `token` no acotado crece indefinidamente. Fuente: [Redis programmability](https://redis.io/docs/latest/develop/programmability/).
6. **Hacerlo distribuido por diseño.** Todos los Gunicorn/Daphne workers, instancias web y workers Celery deben usar el mismo Redis y namespace/version; no confiar en memoria local. Confíe en IP real solo tras configurar correctamente Nginx/proxy y una lista de proxies confiables; de lo contrario el cliente puede falsificar `X-Forwarded-For`. Añada métricas de adquisiciones rechazadas, leases activos, expiraciones y latencia Redis.

### 2. Topes de payload y archivos en Django/DRF

1. **Separar las tres settings.** `DATA_UPLOAD_MAX_MEMORY_SIZE` limita el cuerpo de request que Django carga en memoria (por defecto 2.5 MiB) y excluye los datos binarios de archivos; al excederlo Django lanza `RequestDataTooBig` (`SuspiciousOperation`). `FILE_UPLOAD_MAX_MEMORY_SIZE` no rechaza archivos: selecciona cuándo Django cambia de `MemoryFileUploadHandler` a archivo temporal (por defecto 2.5 MiB). `DATA_UPLOAD_MAX_NUMBER_FIELDS` limita el número de parámetros GET/POST para DoS y lanza `TooManyFieldsSent`; no es un límite de bytes de archivo. Fuente: [Django settings 6.0](https://docs.djangoproject.com/en/6.0/ref/settings/), [Django file uploads](https://docs.djangoproject.com/en/6.0/topics/http/file-uploads/).
2. **Mapear tamaño a 413 explícitamente.** Django puede convertir `RequestDataTooBig`/`TooManyFieldsSent` en respuesta 400 por el manejo general de `SuspiciousOperation`; DRF tampoco garantiza que su handler por defecto produzca 413. Configure un `EXCEPTION_HANDLER` que delegue primero en DRF y, para esas excepciones, devuelva `Response({"detail": ...}, status=413)` (y un código estable). Si Nginx corta antes, devolverá su propio 413: unifique formato mediante `error_page`/proxy o documente ambos. Fuente: [DRF exceptions](https://www.django-rest-framework.org/api-guide/exceptions/), [Django exceptions](https://docs.djangoproject.com/en/6.0/ref/exceptions/).
3. **Aplicar el límite de archivo por rol en una sola capa reusable.** Mantenga constantes por política (`anonymous`, `authenticated`, roles) y un `UploadHandler`/parser común que seleccione el límite después de conocer el usuario; rechace durante el streaming y valide también `UploadedFile.size` en serializer. No intente cambiar settings globales por request. Para multipart, recuerde que Django puede escribir temporalmente antes de la validación; use el handler para cortar temprano. Fuente: [Django upload handlers](https://docs.djangoproject.com/en/6.0/ref/files/uploads/), [Django file uploads](https://docs.djangoproject.com/en/6.0/topics/http/file-uploads/).
4. **Poner un límite coherente en todas las capas.** Configure Nginx `client_max_body_size` como techo absoluto, Django como defensa de aplicación y serializer/handler como política por archivo/rol. Nginx puede devolver 413 antes de Django; `Content-Length` ausente o falsificado no es una autorización: el límite debe aplicarse mientras se consume el stream. Fuente: [Nginx `client_max_body_size`](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size).
5. **Distinguir bytes comprimidos de bytes expandidos.** Un proxy que descomprime, un parser o un archivo comprimido puede tener una relación de expansión enorme. Limite bytes recibidos y, después de descomprimir/parsear, limite tamaño expandido, número de entradas y profundidad; valide MIME por contenido, no por extensión. Nginx/Django no sustituyen límites del parser químico/Gaussian/ZIP.
6. **Probar las rutas reales.** Cubra multipart pequeño/grande, muchos campos, `chunked` sin `Content-Length`, usuario anónimo/autenticado, múltiples archivos y rechazo Nginx. Verifique que no queden temporales y que el JSON/status 413 sea estable. No confunda `FILE_UPLOAD_MAX_MEMORY_SIZE` con “máximo permitido”.

### 3. Endpoints públicos de referencia, solo lectura

1. **Separar datos semilla del dominio de usuarios.** Publique un queryset/modelo o fixture dedicado de referencia, con campos explícitamente serializados y solo `GET`/`HEAD`; nunca reutilice un endpoint de jobs/usuarios con `AllowAny`. Use permisos de objeto y un serializer de salida de allowlist; no exponga IDs internos, owner, inputs, trazas ni resultados privados.
2. **Hacer el contrato versionado y auditable.** Ruta tipo `/api/public/reference/v1/...`; respuesta con `schema_version`, `dataset_version`/fecha y metadatos de procedencia. Cambios incompatibles crean v2. Pruebe que un usuario anónimo no puede enumerar ni inferir recursos privados.
3. **Usar caché HTTP explícita.** Para dataset verdaderamente público e inmutable: `Cache-Control: public, max-age=..., s-maxage=..., stale-while-revalidate=...`, `ETag` fuerte derivado de contenido/version y `Last-Modified`; responder 304 a `If-None-Match`. Si la representación varía por idioma, use `Vary: Accept-Language`; si depende de autorización, no es público y debe ser `private`/`no-store`. Fuente: [Django cache framework](https://docs.djangoproject.com/en/6.0/topics/cache/), [MDN ETag](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/ETag), [MDN Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Cache-Control).
4. **Cachear en reverse proxy/CDN con clave segura.** Permita cachear solo el prefijo público; excluya `/api/auth`, jobs y cualquier respuesta con credenciales. El CDN debe respetar `Vary`, no incluir cookies/JWT en la clave para el catálogo y purgar por versión/tag. Añada `X-Content-Type-Options: nosniff` y límites de respuesta.
5. **Mantener read-only de verdad.** En DRF use `ReadOnlyModelViewSet` o `ListAPIView`/`RetrieveAPIView`, permisos `AllowAny` solo en esa vista, throttling separado y sin acciones custom mutantes. El endpoint no debe aceptar filtros arbitrarios que transformen el catálogo en un exfiltrador; whitelist de filtros y paginación.
6. **No asumir que “público” significa “sin controles”.** Audite licencia, DOI/procedencia, PII y secretos; logging sin payloads sensibles; monitorice cambios y abuso. La caché debe invalidarse cuando se publique una nueva versión.

### 4. `localStorage` para resultados en Angular

1. **Tratarlo como caché pequeña, no base de datos ni seguridad.** Web Storage guarda strings y tiene cuota por origen; los límites y políticas de eviction varían por navegador, modo privado y dispositivo. No hay un “límite universal” fiable: mide/ensaya en los navegadores soportados. Para resultados grandes o muchos jobs, use IndexedDB (estructurado/asíncrono) y, si son reproducibles, el backend. Fuente: [MDN storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).
2. **Capturar `QuotaExceededError` y degradar con gracia.** Rodee `setItem` en `try/catch`; detecte `DOMException` por nombre/código de forma defensiva, elimine entradas antiguas y reintente una vez; si falla, siga mostrando el resultado en memoria y marque caché no persistida. No borre indiscriminadamente tokens ni datos de otra versión.
3. **Implementar FIFO/TTL y presupuesto.** Use claves con namespace (`results:v2:`), índice JSON pequeño con `createdAt`, `lastAccess`, bytes aproximados y job ID; evite `JSON.stringify` duplicado. Al superar un presupuesto configurable, elimine primero expirados y después los menos recientes/antiguos. Una entrada individual debe tener límite propio.
4. **Versionar y migrar el esquema.** Prefije la versión, valide el envelope (`schemaVersion`, `result`, `createdAt`, `expiresAt`), migre solo versiones conocidas y borre de forma selectiva las incompatibles. Nunca confíe en datos del storage para autorización o integridad.
5. **No guardar tokens, credenciales, PII, inputs crudos de otros usuarios ni secretos.** JavaScript/XSS y extensiones pueden leer `localStorage`; almacenar allí datos sensibles amplifica el impacto. Preferir sesión/token en cookie `HttpOnly; Secure; SameSite` cuando el diseño lo permita y mantener resultados sensibles server-side. Fuente: [OWASP HTML5 Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html), [OWASP WSTG browser storage](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/11-Client-side_Testing/12-Testing_Browser_Storage).
6. **Usar IndexedDB al crecer.** Mueva resultados binarios/JSON grandes, índices y consultas a IndexedDB; encapsúlelo detrás de un servicio Angular y conserve `localStorage` solo para preferencias/índice mínimo. Aun IndexedDB está sujeto a cuota y eviction: maneje igualmente `QuotaExceededError`, limpieza y exportación/re-descarga.

## Pitfalls (6 errores comunes)

1. Confundir concurrencia con tasa y usar token bucket/fixed-window para impedir trabajos simultáneos.
2. Hacer `GET count` + `SET`/`INCR` separados: race condition entre instancias; o liberar sin verificar token y borrar el lease de otro trabajo.
3. Confiar en `task_success`/`finally` para siempre: un worker asesinado no ejecuta cleanup; olvidar TTL/heartbeat causa fugas.
4. Creer que `FILE_UPLOAD_MAX_MEMORY_SIZE` rechaza archivos, o que `Content-Length`/Nginx solo basta; olvidar chunked, expansión de ZIP y límites del parser.
5. Exponer un ViewSet privado con `AllowAny`/caché pública: mezcla de queryset, cookies/JWT o `Vary` incorrecto puede filtrar datos.
6. Usar `localStorage` como almacén seguro o ilimitado: guardar JWT/PII, no capturar cuota y sobrescribir todo el storage al migrar.

## Limitaciones

- Las cuotas de almacenamiento, eviction y comportamiento de navegadores cambian por versión, plataforma, modo privado y espacio disponible; deben verificarse en la matriz de navegadores del producto.
- La documentación de Django 6.1 aparece publicada, pero el objetivo indicado es Django 6; las URLs principales fijan 6.0. Validar cualquier cambio 6.1 antes de actualizar.
- “Por IP” no identifica a una persona detrás de NAT y depende de la confianza en el proxy; para abuso serio combínelo con identidad, cuota por cuenta y controles de aplicación.
- Un límite HTTP no valida la semántica ni el coste de descompresión/procesamiento químico; esos límites deben implementarse también en cada parser/plugin.
